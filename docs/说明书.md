## 二·五、类型系统（研发环的地基）

单型 = 职能 × 性质。不再有实现单/工程单/施工单这类只差叫法的东西。旧仓 208 张里修复 26 + 调研 22 + 装配 15 = 30% 靠性质轴才有地方去。

> 这一节有两处真源：**定义与道理**在 `docs/模块.json` 的 类型系统；**机器读的形状**（性质签名、职能表、四层字段、拆单判据）在 `docs/单型/*.json`，`领域/单型` require 的就是那几份。下面的表直接从那里渲染，`书⑮` 盯着 模块.json 不许再抄一份，`书⑯` 盯着每个字段都渲染到了。

### 产出三型

| 型 | 定义 | 验收 |
|---|---|---|
| **方案** | 不确定的，可以有很多种路线。回答「该怎么做」。 | 人判——它是选择 |
| **资产** | 确定的，文件是什么就是什么。策划案、配置表、代码、模型、原画、动画、UI 都是资产。 | 机判为主——存在性、schema、测试 |
| **成果** | 装配的输出：方案与资产整合成可验收的东西（场景、构建、可运行版本）。 | 跑起来——playmode / 构建通过，再人判 |

### 性质四种（定死）

**定死四种，不许加。** 每种是一个输入→输出的签名。评审/QA/审检/核查都不是性质，是闸（见 闸序列）。 进项之外，每张单本身总是输入，表里不再写。真源 `docs/单型/工单.json` 性质签名。

| 性质 | 进 | 出 | 说 |
|---|---|---|---|
| **新建** | 方案? | 资产 | 制作资产。方案是可选进项——有调研在前就吃它的方案，没有就直接做。 |
| **修复** | 资产 | 资产 + 防复发判据 | 修改资产。**必须交一条能红的判据**（H104）——旧仓 26 张修复单里反复出现修过又坏回去，因为没有东西挡回退。 |
| **调研** | （无） | 方案 | 产出方案 |
| **装配** | 方案 + 资产[] | 成果 | 整合方案和资产成可验收的成果。可以有多张，最后一张收尾。 |

### 四层 schema

2026-09-05 01:51–02:12 定。管线是系统（装功能的容器），特性是功能（装专项的容器），专项是实现某特性的步骤，工单是最小单元。**只记直接上级、反向推**（H107）。 真源 `docs/单型/{管线,特性,专项,工单}.json`。

#### 管线

四层之首。管线 = 游戏系统（地图/镜头/时间/UI……），装功能的容器。制作人 2026-09-05 01:51 定：三个字段就够，容器越薄越不分叉。删掉旧仓的 阶段（L0 无定义）。

| 字段 | 类型 | 必填 | 谁写 | 说明 |
|---|---|---|---|---|
| `id` | string，格式 `^P-\d+$` | 是 | 代码 | P-N |
| `名称` | string | 是 |  | 系统名，如「地图系统」 |
| `范围` | string | 是 |  | 一句话：这个系统管什么、不管什么 |
| `状态` | enum：活跃 / 封存 | 是 |  | （默认 「活跃」） |

- 每条管线自带一个散单特性（特性.散单=true），名为「<名称>散单」。无归属的工单挂它——树永远整齐四层。

#### 专项

四层第三层。专项 = 实现某个特性的一段步骤，工单的父级容器（制作人 2026-09-05 01:45 定）。产出类型立项时必填——它就是「完成定义」，旧仓 S-1/S-3 事后补完成定义那两次误催签字，正是缺这一栏。

| 字段 | 类型 | 必填 | 谁写 | 说明 |
|---|---|---|---|---|
| `id` | string，格式 `^S-\d+$` | 是 | 代码 | S-N |
| `名称` | string | 是 |  |  |
| `特性` | ref → 特性 | 是 |  | 直接上级。**不许直接挂管线**，管线从特性推（H107） |
| `产出类型` | enum：成果 / 方案 / 资产 | 是 |  | = 完成定义。立项时必填，不许事后补。决定末单性质与人判要不要 |
| `目标` | string | 是 |  | 一句话：这段步骤做完，什么东西成立了。关账签的是「这句话达成了」，不是「没活在跑了」（旧仓 specials.js:145） |
| `状态` | enum：立项 / 进行 / 收口 / 关账 | 是 |  | （默认 「立项」） |
| `履历` | list | 否 | 代码 | 状态迁移记录 {t, 从, 到, 因, 操作者}。机器写，人不改 |

- 末单规则：专项最后一张子单的性质所产出的类型 == 专项.产出类型。产出=成果 → 末单必然是装配；产出=方案 → 调研；产出=资产 → 新建或修复。**不写死「必须以装配收尾」**——不产成果的专项会被逼塞假装配单。
- 装配单可以有多张（分批整合），只要最后一张是。
- 关账是唯一人闸：产出类型 ∈ {成果, 方案} 时制作人签；产出=资产 时闸序列过了自动收口（项管不逐张看）。
- 专项是可选的：一张单就能交的活直接挂散单特性，不立专项。多张单合起来才有一个完成定义的，才立。

### 拆单判据

项管拆完，机器判「拆得对不对」；审批那道人闸只看该不该做，不看格式。**四条在 schema 层判、每条都能红（领域/单型）；③ 在取单器判。** 真源 `docs/单型/工单.json` 拆单判据。

- ① 每张单有归属（专项 或 散单特性）且指向的东西存在——归档时没归属 → 红。旧仓 14 张孤儿单再也长不出来
- ② 进项的每一项：由同专项内更早（按创建时间）的单产出，或已存在于盘上——这一条取代「专项必须先调研再新建」那类清单：产出=成果→末单装配→装配要方案→方案须由更早的调研产出，顺序自己推出来
- ③ 进项未过闸不派（取单器判，不在 schema 判）——没验收的方案不许当输入
- ④ 若有专项，末单性质产出 == 专项.产出类型（只在专项 收口/关账 时判）
- ⑤ 职能 × 性质 的组合合法：职能在表里且启用，性质 ∈ 该职能的 可接性质（性质写进了职能权限）

### 闸序列

`[初检(机判)] + [深检] + (产出 ∈ {方案, 成果} ? [人判] : []) + (争议 ? [仲裁] : [])`　评审/QA/审检/核查全是闸，签名统一：资产|方案|成果 → 通过|打回|上呈。序列由产出类型推出来，**三轮审检 A/B 不用再问**。 资产走两闸自动完结（项管不逐张看）；方案与成果多一道人判。制作人只验方案和成果——这就是他说的「只验管线/特性/专项/保留单」在类型系统里的形态。

### 双链

思维要——单指向资产、资产反查到单。 Obsidian `[[ ]]` 语法不要。实测数据区 `[[ ]]` 只有 18 条，frontmatter 带类型的边有 229 条；带类型的边分得出「修复了」与「依赖」，`[[ ]]` 分不出。 **正向存、反向推**（H107 一个事实一处）。单的 frontmatter 存 进项.资产 与 防复发判据（测试路径）；资产的履历页是生成的不存。 上下文包装配时——新单引用某资产，编排/装配器自动带上它的履历（历次修复与判据）。不靠人去翻。**等 领域/记忆 建了才接：现在 编排/装配器 不装履历。**

### 方案存法

方案存成文件：数据区/方案/<单号>-<名>.md。存储上它是文件（可按路径引用、可版本化），验收上它是方案（人判）——**存法与验收方式是两回事**。 调研单 frontmatter 写 产出: 方案/<路径>；下游单写 进项: {方案: <路径>}。正向存，反向（这个方案被谁用过）是生成的索引。 执行者不找。取单器验进项已过闸 → 编排/装配器派单时把方案文件直接塞进上下文包 → 送到手上。这是昨夜 Q9 上下文包在研发环的具体形态。

- **领域/额度** —— 额度水位与预算闸。旧仓两边各算一份、字段名都不同。
- **领域/记忆** —— 记忆条目的检索：按当前这张单/这一席，挑出该带进上下文的那几条。旧仓只有存储没有检索——记忆库是文稿台的一个根，写得进去、取不出来。
- **领域/文稿** —— 文档的分类、标签、筛选。哪些是策划案、哪些是协议、哪些是回执——按类型和标签找得到。

### 编排（7）

- **编排/引擎** —— Unity 通道。外部命令方式调，不 require。要带编辑器租约——白天人在用同一个工程时抢锁是现成的暴露面。
- **编排/巡检** —— 看门狗与后台循环。每一条都要能说出「它坏了会怎样」。
- **编排/评审台** —— 异厂评审：各厂领一份立场卷、互不可见、独立出意见。两厂撞到同一落点是最强的信号。
- **编排/情报** —— 抓源、去重、打分、入库。源挂了要说是哪个源挂了、连败几次，不许出一份空日报当正常。
- **编排/适配器-codex** —— codex exec 那家。有 PreToolUse（Bash/apply_patch，exit 2 或 deny 实跑拦下）+ .rules 命令白名单，写闸能硬。本机 Windows 无头沙箱不可用、MCP 工具绕过沙箱已实证——写闸放 hook 层不放沙箱层。细节见 docs/harness四家对照。
- **编排/适配器-hermes** —— Hermes Agent（NousResearch v0.21.0，MIT，Python）——是 harness 不是模型。三层 pre_tool_call、写路径硬拒、SQLite+FTS5 中文检索，兼知识库管理员候选。细节见对照表。
- **编排/适配器-dsh** —— DeepSeek harness（0.1.2-alpha）。headless 只走 argv 无 stdin、无 usage、会话 zstd 不可直读、resume 只有 ACP、明写会破坏性变更。四家最弱，最后接。细节见对照表。

### 接口（4）

- **接口/prod** —— 生产：工单、闸、排程、台账。
- **接口/seat** —— 席位：名册、协议、私聊、说话。
- **接口/obs** —— 观测：事件流、班次、监视、存照。
- **接口/doc** —— 文稿台的口：列目录、读、写、锁、版本环。写一律过内核/写闸，这一层不自己碰 fs。

### 哨兵（2）

- **哨兵/主循环** —— 探针 → 判定 → 扶起 → 留痕。**不监听端口不算活着**——旧仓那座塔就是因为不监听端口、进程名又是 node.exe，一次核对完整漏过它。
- **哨兵/逃生页** —— 产线死了也能看见「为什么死的」。单文件、内联样式、零 bundle 依赖。

### web（5）

- **web/对话** —— 群聊与私聊、在座栏。
- **web/生产** —— 闸、在途、排期、甘特、工单库。
- **web/观测** —— 监视、班次、事件流、存照。
- **web/文稿** —— 文稿台与编辑器。
- **web/席位** —— 席位页与在座栏：名册、协议两层、选模型、权限卡、未选模型时明说缺什么并给出下一步。
